    **Final-residual guard.** A solve whose assembled solution leaves any equation's residual above `max(1e-6, 100·rel_tolerance)`, relative to that equation's own top-level terms, now fails with the equation quoted instead of reporting `ok` (`engine::unconverged_equation`, applied in `PreparedDocument::assemble_solution` for solve, sweep rows and all-roots). This is the path by which the merge rescue once returned a 1.2e4 residual as success. Across the 843 converged corpus solves the worst relative residual is 1.3e-7, so no golden changes.

    **DYNAMIC unit check (2026-10-22).** `DYNAMIC` bodies and their scalar initial conditions now reach the unit checker in `check`, the prepared solve and the ODE-only shortcut, through one helper (`engine::unit_check`).
    - `der(X)` carries X's units per second when X has real units. For a dimensionless state, whose model is unitless, it stays a wildcard.
    - A bare-number initial value (`x(0) = 0`) declares nothing.
    - The time variable is a wildcard.
    - `If(...)` now carries its branch units instead of reading as dimensionless.
    - Method-of-lines `FOR` blocks and array-state initials are checked too (2026-10-23, see the fifth paragraph below).

    The check exposed one library defect. SigPID's clamped anti-windup was `der(ie) = e + (out.sig - u_raw)/Taw`, which balances only with Taw in output-per-measurement units. It is now `/(Ki·Taw)`, so Taw is a reset time in seconds (owner decision 2026-10-22). Every affected example states `Taw = old/Ki`, so results are unchanged. `ev-battery-cooling-pid`'s input changed with provenance, and its expected output did not. It also exposed bare component parameters in 2 Help examples, 4 reference pages and 2 gallery models, which now carry units.

    **Component parameter units (2026-10-22).** A component header's `Resistor(R [ohm])` unit now reaches `components::def::Param`. A bare instance value under it is typed for the checker (`R=10` is 10 Ω), never scaled. 255 parameters of 105 components in `library-data/` declare the units their reference pages stated. `parse-library.mjs` reads them, so the header is the wizard's unit source, and the generated catalogs did not change. No example warned. One test had pinned the Java engine's false "right side [A]" warning on an untyped resistor; it now asserts none.

    **Table and plot checklist audit (2026-10-23).** The September reviews (T1–T15, F1–F12; recovered from `0b116de^:docs/`) were walked item by item against the code, not test titles. All fifteen table items and eleven of the twelve plot items were already fixed and pinned by a test, mostly in `tables.precision.test.ts`, `tableValidation.test.ts`, `tableGridModel.test.ts`, `csv.test.ts`, `composeTables.test.ts`, `solve_table.rs` and the `plots/` suites. T3 now has an App-level test as well; see the cross-layer paragraph below.

    **Method-of-lines unit check (2026-10-23).** `FOR` blocks inside `DYNAMIC` and array-state initials (`T[2](0) = T_init`, `T[1:N](0) = …`) now reach `engine::unit_check`. Loop bounds such as `N` are solved values, unknown at check time, so each loop body is lowered once rather than expanded (`MolArrays`). An array indexed anywhere by something other than a literal is one field and reads as a single variable, so the boundary `T[1] = T_left` and the initials ground the loop body. An array indexed only by literals keeps one variable per element, because a state vector may mix position and velocity. A loop variable reads as a dimensionless 1. Pinned by `method_of_lines_bodies_and_array_initials_are_unit_checked`; all 809 doc blocks still check at zero unit warnings.

    **Component parameter descriptions and units (2026-10-23).** The 162 component pages with two-column parameter tables now have three, each parameter described from the component's own equations, and their library headers declare the units: 489 newly typed parameters, dimensionless ones as `[-]`. BatteryCellMap's page also gains the four header parameters it had dropped (`R1`, `C1`, `k_cal`, `Ea_cal`). A parameter whose unit depends on its wiring stays untyped and says so on its page: signal levels and gains; Economizer's `lim` and `band`, which are K or J/kg by variant; and the signal time parameters that meet `time` or an untyped gain (SigSine `freq`, SigStep/SigRamp/SigPulse `t0`/`width`/`eps`, SigRateLimiter and SigPID `tau`). Typing those made three reference examples warn, because a steady document pins a bare `time = 0.125` and bare gains read dimensionless. Pure filters keep `[s]` and `[rad/s]`. All 809 doc blocks check at zero unit warnings, and the regenerated catalogs only gain units and descriptions.

    **Cross-layer acceptance (2026-10-23).** Two journeys in `e2e/phase9-journeys.spec.ts` drive the built app:

Journey 5's solve now runs about twice as long as landing its edit needs, and the edit swaps in a one-line document so the follow-up solve is instant. The cross-browser e2e now runs as its own CI job (`e2e`) inside `mcr.microsoft.com/playwright:v1.62.1-noble`, on the `dist` the web job uploads: `playwright install --with-deps` went through apt and hung on the Azure mirror three times on 2026-10-23 (40 min, then twice into a 10-min cap) before any test ran. - **`ThermalFuse`** is a smooth current-threshold resistance (`Iblow`, `kR`, `epsI`, a tanh law). It has no thermal state and no irreversible trip, so neither a thermal fuse nor an I²t fuse is modelled yet.
- **`SigRelay` and `SigSwitch`** are smooth tanh blends, not hysteresis. Hysteresis needs a discrete-state contract (deferred, below).
- **Steady sliders.** They already re-solve, debounced at 220 ms during a drag and 30 ms at commit (`App.tsx` `scheduleSliderSolve`). The bridge's `solve` keeps no `PreparedDocument` between requests: `crates/frees/src/lib.rs` has none, and reuse happens only inside one sweep or analysis job.
- **Stepping seams.**
  - `dae/solver.rs` `IdaDaeSolver` already has `init`, `reinit` and `step(tout)`, and events already use `reinit` + consistent initial conditions.
  - The explicit driver (`ode/integrator.rs` `integrate`, `DynamicSolver::solve_with`) runs t0→tf in one call.
  - The ODE-only path of `solve_with_pins_and_warm` runs the full dynamic solve. **Live must not be built by re-solving with growing end times**: that restarts trajectories, repeats work, drops multistep history and mishandles events.

- **F. Decisions and baseline — done 2026-11-07 (`f-decisions-baseline`).**
  1. **Decisions.** The owner told me to run the whole programme ("run until finish all phases", 2026-11-06), so each default below was set then. Any of them can be revisited.
     - **Live vs playback.** Live is a separate mode labelled **Live**. RUN-05 Playback keeps its rule that it never solves. A finished live run hands its recording to Playback.

     - **Runtime inputs.**
       - A pinned slider parameter applies at the next accepted time with the states held. The algebraic variables are made consistent again (IDA `reinit` plus a consistent initial condition), and the change is logged as an input event.
       - A parameter that appears in an initial condition needs a Reset.
       - A change to a storage parameter (C, mass, volume) is applied with its state held. The bar says so: the state is kept and the stored energy changes.
       - A structural edit ends the session.
     - **Recording.** The last 50,000 samples per run are kept in memory. They are not saved in the project; CSV export carries them out.
     - **Interpolation.** None. Live shows the newest accepted sample, and only particle motion is animated between samples.
     - **Losses.** There is no new library convention. M's power view is computed from port quantities the engine already reports: V·I, Q̇, τ·ω and ṁ·h per port. So it needs no change to the library.
     - **Electrical scope.**
       - In scope: `Switch` (signal-driven), sine and controlled V/I sources, `IdealTransformer`, ideal `OpAmp`, `Zener`, `Potentiometer`, NTC `Thermistor` and electrothermal `Lamp`.

  2. **Measurement.** Taken on an i7-1185G7 at `aeaaede`, native `--release`, with the WASM module in Node 22 for comparison.
     - **Steady re-solves.**
       - *Fresh* is today's slider path: apply the override, then a full solve.
       - *Prepared* reuses a `PreparedDocument` and pins the value.
       - *Warm* is prepared, plus a Newton start from the previous move's solution.
       - Each move changes the value by 1–3 %. All columns are native medians.

       | Model | Fresh | Prepared | Warm | Warm vs fresh values | WASM fresh |
       | --- | --- | --- | --- | --- | --- |
       | Small: pumping main, 33 blocks, pin `Q` | 6.7 ms | 6.3 ms | **0.06 ms** | 3.6e-15 | 18.6 ms |
       | EV thermal, 180 blocks, pin `k_fin` | 4.7 ms | 2.0 ms | **1.5 ms** | 9.7e-14 | 12.4 ms |
       | 500-component floor, 2,185 blocks, pin `P_set` | 7.4 s | 7.6 s | 8.9 s | 1.6e-13 | — |
     - **Findings.**
       - Preparation is a small share of a re-solve: 0.2–18 ms against seconds on the large model. The win is the warm start: 3× on EV and 100× on the small model.
       - On the 500-component floor, neither helps. Its 7 s is Newton on 2,185 blocks from cold guesses, and the warm start does not shorten it. A slider on that model stays a deliberate, slow action.
       - Prepared values differ from fresh ones by round-off on EV: 7 values differ bitwise, all under 1e-9 relative. G's acceptance is therefore round-off agreement (1e-12 relative), not bitwise equality.
       - WASM in Node is 2.6–3× slower than native.
     - **Dynamic step cost.** A 50-state linear thermal chain, 0–1000 s, 1,001 output samples:
       - IDA 3.3 ms (WASM 17.9 ms);
       - ode45 56 ms (WASM 152 ms);
       - radau5 364 ms.
       Live stepping on IDA therefore has two orders of magnitude of headroom inside a 5–15 ms chunk. ARCHITECTURE §10's target holds with room to spare.

- **K. Live mode MVP (stages 1–2; architectural).**
  1. **Engine `LiveSession` (`frees-core`).**
     - It owns the immutable prepared structure, apart from the mutable state: t, y, y′, step size, BDF history, event state and the pin vector.
     - API: `open`, `advance(t_target, work_budget)`, `pause`, `step(kind)` and `reset`/`dispose`. `step(kind)` is one of: accepted step, output sample, next event.
     - `advance` returns only accepted output samples and event hits.
     - IDA comes first. The explicit ode45/radau5 driver is refactored into a resumable stepper with the same tolerances.
     - Tolerances are never relaxed for frame rate.
  2. **Bridge and worker.**
     - Exports: `live_open`, `live_advance` (a `Float64Array` chunk plus a JSON header), `live_set`, `live_pause`, `live_reset` and `live_dispose`.
     - A dedicated worker outside the sweep pool owns the session.
     - **Pull model:** the main thread asks for `t + speed·Δt_wall` on each animation frame, with at most one request in flight. Each reply stays within a work budget of roughly 5–15 ms, so commands are serviced between chunks.
     - Every message carries the session, revision, generation and chunk sequence. Buffers are recycled.
  3. **Live bar.**
     - It is labelled **Live**, never Playback.
     - Controls: Run/Pause, the three kinds of step, Reset, and a log-scale speed in sim-seconds per wall-second.
     - It shows sim time, the achieved speed ("×0.3 of requested") and the step size.
     - Structural edits pause the session and close it through the revision tracker.
  4. **Results store and failure.**
     - **Results store.** One store per block (a ring buffer) feeds the diagram, readouts, H's particles and cursor, and plots, all from one accepted timestamp. On stop it becomes a normal ODE table whose run identity includes the input log, so RUN-05 playback, RUN-07 comparison and CSV export work on it unchanged.
     - **Failure.** On a failure, the session pauses at the last accepted state with the existing diagnosis and owning block. It offers retry with a smaller maximum step. It never publishes a NaN state as success.
  - **Acceptance.**
    - Chunked and batch runs agree at common output times: bitwise for IDA, and within the integrator's own tolerance otherwise.
    - Pause and resume preserve history.
    - Memory stays bounded over a 30-minute run.
    - Stale-generation messages are dropped.
    - A worker trap respawns cleanly.
    - Commands are serviced within one chunk on small, EV and large models.
    - Measured against F's baseline, and within D3 and the WASM budget.
  - **K1 done 2026-11-07 (`k1-live-session`): the engine `LiveSession`, IDA blocks.**
    - **One driver for batch and live** (`ode/live.rs`). `IdaRun` is the IDA output loop of a `DYNAMIC` block, holding as owned state what `solve_with_ida` kept in locals: the parked integrator, the grid position, and how the run ended. The batch solve is one `advance` over the whole grid; a live session makes the same calls in pieces. Chunked rows therefore equal batch rows by construction, and the tests prove it across chunk boundaries.
    - **No borrow between calls, no `unsafe`.** `frees-core` forbids `unsafe`, so the session cannot hold a solver that borrows its own definitions. Instead `IdaDaeSolver::rebind` moves the whole state (BDF history, step size, Jacobian and LU, root state) onto a residual rebuilt from the owned `AssemblySpec` at each chunk. Between chunks it is `parked`, pointing at a residual that refuses to evaluate. The rebuild costs about 57 µs per chunk on a 61-unknown model.
    - **API.**
      - `PreparedDocument::open_live(block)` runs the steady solve and returns the steady solution with the block's session at `t0`.
      - `advance(t_target, budget)`: the budget sees the chunk so far between rows and ends it early after at least one row.
      - Steps: `step_sample` (the next row), `step_event` (to the next crossing) and `step_accepted` (one internal step, in a new IDA one-step mode that shares `step`'s re-entry and stepping code). The accepted-step state comes back beside the rows.

      - A live run continues past `tf` on the same grid formula, so its rows up to `tf` are the batch rows.

### Native desktop & iOS (Tauri v2) — proposal only

No Tauri project exists and no build has been measured.

**Why the port is cheap:**

- There is no cross-origin isolation or network dependency.
- The engine boundary is already `&str → String` (`crates/frees/src/lib.rs`), and `frees-cli` already calls it natively.
- `call(...)` in `engineClient.ts` is the single dispatch seam.

**Hard constraint — thread affinity.** The REPL session, progress sink and deadline predicate are `thread_local!`, so the native side needs one dedicated `std::thread` per worker index, with index 0 REPL-affine. A Tokio blocking pool would lose the session.

**Phases:**

1. `src-tauri/`, excluded from the root workspace (or the wasm32 clippy gate breaks). CSP keeps `'wasm-unsafe-eval'`.
2. A `tauri` Vite mode without the PWA/build-info plugins, with `base: './'`. Keep `legacy-peer-deps`.
3. Per-index engine threads, with `ipc::Channel<f64>` for progress. Use the JSON envelopes, not `*_zerocopy`.
4. One `saveBlob` helper replacing the six anchor-download copies; `openPrintReport` is the hardest item.
5. A `build-tauri` release matrix, unsigned.
6. iOS, which needs macOS/Xcode.

**Accepted ceilings:**

- JSON envelopes, not binary IPC.
- Stop cancels only transients.
- The `localStorage` quota is unchanged.

**Acceptance:**

- Every §4 gate stays green unchanged.
- A dispatch-layer test covers every method name.
- Manual smoke: solve parity, sweep progress, Stop, two-call REPL affinity, exports, reopen, print.
